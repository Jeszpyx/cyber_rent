# Cyber Rent — план и дорожная карта

Экономическая настольная игра (механика «Монополии», свой киберпанк-сеттинг): Vite + React SPA, раздаётся через Express на MonsterASP, работает как сайт и как Telegram Mini App.

## Контекст

Проект деплоится на https://cyber-rent.runasp.net через Git deploy в панели MonsterASP (Node.js SSR, iisnode).

Цель — своя игра по механике «Монополии» в киберпанк-сеттинге. Названия, валюта и тексты карточек свои, без чужих торговых марок. Игра работает и как сайт, и как Telegram Mini App (бот у пользователя уже есть), поэтому интерфейс адаптивный.

**Этап 1 (делаем сейчас):** рабочий прототип, который можно захостить, открыть из бота и сыграть против ботов: бросить кубики, походить, купить поле, заплатить ренту, открыть карточку поля. На экране видна версия сборки, чтобы проверить, что обновления из git доходят до хостинга.
**Этап 2+:** дорожная карта из маленьких шагов для более слабых ИИ-агентов. Сохраняется в репозиторий как `docs/ROADMAP.md`.

## Принятые решения

- **Стек:** Express 5 + TypeScript 6 (сервер), Vite 8 + React 19 (клиент), Vitest 5 (тесты движка). Нужен **Node ≥ 22.12** (требование Vite 8 / Vitest 5). На хостинге Node 22.20, версия показывается в `/api/health`.
- **⚠ Не обновлять TypeScript до 7.x.** TS 7 — нативный Go-компилятор, запускается как `tsc.exe`, а MonsterASP запрещает запускать `.exe` при сборке (`spawnSync … tsc.exe UNKNOWN`). Нельзя и другие инструменты сборки, которые запускают нативные бинарники дочерним процессом.
- **Документация:** перед использованием API библиотеки сверяться с актуальной документацией через Context7 (скилл `context7-cli`: `npx ctx7@latest library <name> <query>` → `npx ctx7@latest docs <id> <query>`). Версии мажорные и новые, не полагаться на память.
- **Express 5:** catch-all маршрут пишется как `'/{*splat}'`, а не `'*'`.
- **TypeScript:** `moduleResolution: node/node10`, `baseUrl`, `target: es5` устарели (удалены в TS 7), не использовать. Сервер собирается с `module: nodenext` (без `"type": "module"` в package.json → CommonJS).
- **Игровая логика** — чистые функции в `src/shared/game/`, без React и Node API. На этапе 1 работает в браузере; позже тот же код переедет на сервер для мультиплеера.
- **Один корневой `package.json`, без workspaces.** Панель MonsterASP запускает `npm install && npm run build` для выбранного `package.json` и публикует всё вместе с `node_modules`.
- **Всё нужное для сборки лежит в `dependencies`, а не в `devDependencies`:** `typescript`, `vite`, `@vitejs/plugin-react` и `@types/*`. Неизвестно, ставит ли панель dev-зависимости (при `NODE_ENV=production` не поставит), а без них упадёт `npm run build`. В `devDependencies` — только `vitest`.
- **Сервер компилируется в CommonJS** (`dist/server/index.js`): iisnode грузит entry через `require`, с ESM-точкой входа бывают проблемы.
- **`process.env.PORT` передаётся как есть, без `parseInt`.** Под iisnode это named pipe, а не число.
- **Валюта:** кредиты `₵`. Тема: районы мегаполиса, корпорации, монорельс, «Изолятор» вместо тюрьмы.

## Этап 1 — реализация (✅ выполнено)

### 1. Сборка и сервер
- `package.json` scripts:
  - `"build": "tsc -p tsconfig.server.json && vite build"`
  - `"start": "node dist/server/index.js"`
  - `"dev": "vite"` (клиент с HMR; серверу в dev запускаться не обязательно)
  - `"test": "vitest run"`
- `src/server/index.ts`:
  - `express.static(dist/client)`: для `/assets/*` (хэшированные файлы) `Cache-Control: public, max-age=31536000, immutable`.
  - `index.html` отдаётся с `Cache-Control: no-cache`. Иначе Telegram WebView держит старую версию, и «обновления не подтягиваются».
  - `GET /api/health` → `{ ok: true, node: process.version, startedAt }` для быстрой проверки деплоя.
  - Fallback `app.get('/{*splat}')` → `index.html`.
  - Путь к `dist/client` через `path.join(__dirname, '../client')`.
- `.gitignore`: `node_modules`, `dist`.
- `vite.config.ts`: `define: { __BUILD_TIME__: JSON.stringify(new Date().toISOString()) }`. Commit hash на хостинге может быть недоступен (неизвестно, копирует ли панель `.git` в `/.source`), поэтому основной маркер — время сборки.

### 2. Игровой движок (`src/shared/game`) — MVP-правила
- 2–4 игрока (1 человек + 1–3 бота), старт 1500₵.
- Бросок 2d6, движение по 40 клеткам; за проход «Старта» +200₵.
- Свободную собственность (район / транспорт / утилита) можно купить или отказаться (без аукциона в MVP).
- Рента: район — базовая (×2 при монополии группы); транспорт — 25/50/100/200 по числу транспортных клеток у владельца; утилиты — 4× или 10× сумма кубиков.
- Налоговые клетки: фиксированная плата.
- «Взлом» / «Сеть» (аналоги шанса и казны) в MVP: событие «клетка-заглушка» в логе, без эффекта.
- «Отправка в Изолятор» в MVP: просто перенос на клетку Изолятора, без пропуска ходов.
- Дубль → ещё один ход (без правила трёх дублей в MVP).
- Банкротство: деньги < 0 → игрок выбывает, собственность возвращается банку. Остался один — победа.
- Состояние хода: `phase: 'roll' | 'buyDecision' | 'end' | 'gameOver'`.
- Action: `ROLL`, `BUY`, `SKIP_BUY`, `END_TURN`. Каждое применение пишет события в `state.log`.
- RNG хранится в состоянии как `seed`, результат детерминирован.
- `bot.ts`: покупать, если `money − price ≥ 200`; иначе пропустить.

### 3. Клиент
- `useGame`: `useReducer(applyAction)`. Если текущий игрок — бот, `useEffect` с `setTimeout(700ms)` диспатчит `decideBotAction`, чтобы ходы ботов было видно.
- Доска: квадрат `aspect-ratio: 1`, `width: min(100vw, 100dvh − высота панели)`. На узком экране (<768px) панель под доской, на широком — справа.
- Клетки на телефоне ~30px: цветная полоска + 1–2 слова. Тап → `CellCard` с полной информацией.
- Фишки игроков — цветные кружки на клетке.
- `telegram.ts`: `WebApp.ready()`, `WebApp.expand()`, цвета из `themeParams` в CSS-переменные, `disableVerticalSwipes()` при наличии, чтобы свайп не закрывал приложение.
- Вне Telegram всё работает как обычный сайт.

### 4. Тесты движка (`engine.test.ts`)
- Проход через Старт даёт +200.
- Покупка списывает деньги и назначает владельца.
- Рента переводится владельцу; при монополии удваивается.
- Банкротство выбывает игрока; последний оставшийся → `gameOver`.
- Одинаковый seed → одинаковая партия.

### 5. Деплой и Telegram (делает пользователь)
1. `git push` → в панели **Pull latest** → **Build & publish** (Start command: `dist/server/index.js` → **Save**).
2. Проверить https://cyber-rent.runasp.net/api/health и видимое время сборки на странице.
3. Проверить, что включён HTTPS (раздел HTTPS в панели): Telegram открывает Mini App только по https.
4. В @BotFather: `/mybots` → бот → **Bot Settings → Menu Button** → URL `https://cyber-rent.runasp.net` (или `/newapp` для ссылки вида `t.me/<bot>/<app>`).
5. Открыть бота в Telegram → кнопка меню → игра.
6. Проверка обновлений: поменять текст → push → Pull + Build & publish → переоткрыть Mini App → время сборки новое.

## Дорожная карта для агентов (→ `docs/ROADMAP.md`)

Правила для агента, которые записываются в начало файла:
- Один шаг = один PR/коммит. Не трогать файлы вне указанных без необходимости.
- Логика только в `src/shared/game` (чистые функции, без React/DOM). UI только отображает состояние и диспатчит Action.
- Каждое изменение правил сопровождается тестом в `src/shared/game/*.test.ts`. `npm test` и `npm run build` должны проходить.
- Данные (клетки, карточки, цены) — в файлах данных, не в коде логики.
- Никаких оригинальных названий и терминов «Монополии» (Monopoly, Boardwalk, Chance, Community Chest и т. п.).

### Блок A — Карточки событий (✅ выполнено)
Реализация: данные в `cards.ts`, эффекты — `applyCard` в `engine.ts`, тесты в `cards.test.ts`. Вытянутая карточка переводит игру в фазу `'card'` (`state.pendingCard`), эффект применяется по Action `APPLY_CARD`. Для эффекта `repairs` в `GameState` уже есть `buildings` (1–4 модуля, 5 = небоскрёб, `TOWER_LEVEL`); блок C должен использовать это поле. Карточки освобождения лежат в `player.releaseCards`, после использования (B2) их нужно вернуть под низ колоды.
- **A1.** `src/shared/game/cards.ts`: типы `Card { id, deck: 'hack' | 'net', text, effect }`; `effect` — размеченное объединение: `money`, `moveTo`, `moveBy`, `goToIsolation`, `payEachPlayer`, `collectFromEachPlayer`, `getOutOfIsolation`, `repairs`.
- **A2.** По 16 карточек в колоды «Взлом» и «Сеть», тексты в киберпанк-теме.
- **A3.** Колоды в `GameState`: перемешать seeded RNG при создании, тянуть сверху, класть вниз.
- **A4.** Обработчики эффектов `money` / `moveTo` / `moveBy` + тесты (при `moveTo` через Старт — +200).
- **A5.** Остальные эффекты + тесты.
- **A6.** UI: модалка вытянутой карточки с кнопкой «ОК» (боты закрывают автоматически).

### Блок B — Изолятор (тюрьма) (✅ выполнено)
Реализация: `engine.ts` (`resolveRoll` → `rollInIsolation`, `sendToIsolation`, `release`, Action `PAY_BAIL` / `USE_RELEASE_CARD`), решение бота `decideInIsolation` в `bot.ts`, тесты в `isolation.test.ts`. Константы `BAIL`, `ISOLATION_ATTEMPTS`, `DOUBLES_TO_ISOLATION` лежат в `board.ts`. Новые поля: `player.isolation: { turnsLeft } | null` и `state.doublesInRow` (сбрасывается в `nextPlayer` и `sendToIsolation`). Новая фаза `'isolation'`: `nextPlayer` ставит её задержанному вместо `'roll'`. В ней допустимы `ROLL` (попытка дубля), `PAY_BAIL` (только при `money ≥ BAIL`) и `USE_RELEASE_CARD` (карточка уходит под низ своей колоды). После залога или карточки начинается обычный ход (`'roll'`, дубли дают повторный бросок). Дубль из Изолятора освобождает и двигает фишку без повторного хода. После последней неудачной попытки залог списывается принудительно (может обанкротить), затем фишка идёт на сумму кубиков. Рента в Изоляторе начисляется как обычно. Задел: штраф за бездействие (D2) и онлайн-таймаут должны учитывать фазу `'isolation'`; аукцион или обмен карточек освобождения (E3) используют `player.releaseCards`.
- **B1.** `player.isolation: { turnsLeft } | null`. Три дубля подряд → в Изолятор.
- **B2.** Выход: заплатить 50₵ / выбросить дубль (до 3 попыток) / карточка освобождения. Action `PAY_BAIL`, `USE_RELEASE_CARD`.
- **B3.** Решение бота в Изоляторе.
- **B4.** UI: кнопки в панели и значок на фишке.

### Блок C — Экономика и застройка (✅ выполнено)
Реализация: данные в `board.ts` (`rent: RentTable` на 6 уровней у районов, `GROUP_BUILD_COST`, `BANK_MODULES` / `BANK_TOWERS`, `MORTGAGE_RATE`, `MORTGAGE_INTEREST_PERCENT`, `TRANSIT_RENT`, `UTILITY_MULTIPLIERS`). Чистые проверки и расчёты вынесены в `economy.ts`: `canBuild` / `canSellBuilding` / `canMortgage` / `canUnmortgage`, `bankStock` (остаток у банка считается по `state.buildings` и отдельно не хранится), `liquidationValue`, `actingPlayer`. Их используют движок, бот и UI. Мутации сделаны в `engine.ts`, тесты лежат в `economy.test.ts`. Новые поля: `state.mortgaged: Record<index, true>` и `state.debt: Debt | null`. Новые Action: `BUILD` / `SELL_BUILDING` / `MORTGAGE` / `UNMORTGAGE` (с `index`), `PAY_DEBT`, `DECLARE_BANKRUPTCY`. Строить, продавать, закладывать и выкупать можно только в свой ход в фазах `roll` / `isolation` / `end`. Продавать и закладывать можно ещё и в фазе долга.
- **Все обязательные платежи идут через `settle(state, payments, then)`, а не напрямую.** Если наличных хватает, деньги просто переводятся. Если наличных мало, но хватит вместе с продажей построек и залогом, включается новая фаза `'debt'`. Если не хватает и этого, игрок сразу банкротится перед получателем платежа. В фазе `'debt'` решение принимает должник (`actingPlayer`), и это не обязательно текущий игрок: например, при карточке «собери с каждого». `useGame` и UI смотрят на `actingPlayer`. В `debt.queue` лежат оставшиеся платежи (например, «заплати каждому»), в `debt.then` указано, чем продолжить ход: `'finish'` или `'move'` (выход из Изолятора после принудительного залога).
- Правила, которые я выбрал сам. Небоскрёб возвращает банку 4 модуля. Если у банка меньше 4 модулей, при продаже небоскрёба на клетке остаётся столько модулей, сколько есть у банка, а недостающие сразу выкупаются за полцены. Заложенная клетка не ломает монополию для удвоенной базовой ренты, но в квартале с заложенной клеткой строить нельзя. Заложить район можно, только если во всём квартале нет построек. Кредитор получает от банкрота всё: наличные, стоимость построек по цене выкупа банком, клетки вместе с залогами (без процента за переоформление) и карточки освобождения. При банкротстве перед банком клетки освобождаются, залоги снимаются.
- Бот (`bot.ts`). В фазе `end` выкупает залоги и строит, если после траты остаётся не меньше 300₵ (`BOT_BUILD_RESERVE`). В долге сначала закладывает клетки вне монополий, потом продаёт постройки, потом закладывает остальное, затем платит `PAY_DEBT`.
- UI. На клетке модули показаны зелёными квадратами, небоскрёб красным, заложенная клетка заштрихована. В `CellCard` есть таблица ренты, залог и выкуп, а владельцу в его ход показываются кнопки действий. В центре доски в фазе долга выводится подсказка и кнопки «Заплатить» и «Сдаться».
- Симуляция: `npm run simulate [-- <партий> <ботов>]`, компилируется через `tsconfig.sim.json` в `dist/sim`. Результат на 1000 партиях по 4 бота с лимитом 1000 ходов: победителем завершается только ~31% партий, средняя длина ~272 хода (~68 кругов), винрейт по позициям 7.9 / 9.6 / 7.8 / 5.7%. Причина: без обмена монополии у ботов складываются редко, после раскупки поля партия идёт по кругу. Это нужно исправлять в блоке E (аукцион и обмен) и D4 (лимит ходов).
- Задел: штраф за бездействие и онлайн-таймаут (D2) должны учитывать фазу `'debt'`, где решает должник, а не текущий игрок. Штрафы в копилку «Нейтральной зоны» (D1) нужно проводить через `settle` с `to: null`. Аукцион и обмен (E) должны учитывать `mortgaged` и запрет передачи клеток с постройками. В онлайне (G) нужно проверять, что Action пришёл от `actingPlayer`.
- **C1.** Таблица ренты района: `rent[0..5]` (без построек, 1–4 «модуля», «небоскрёб»). Вынести в `board.ts`.
- **C2.** Action `BUILD` / `SELL_BUILDING`: только при монополии и равномерной застройке. Тесты.
- **C3.** Лимит построек у банка (32 модуля / 12 небоскрёбов).
- **C4.** Залог (`MORTGAGE` / `UNMORTGAGE`, +10% при выкупе). На заложенной клетке рента не берётся.
- **C5.** Банкротство перед игроком: собственность переходит кредитору, а не банку.
- **C6.** Бот: строит, когда есть монополия и запас ≥ 300₵; закладывает при нехватке.
- **C7.** UI: иконки построек на клетке, кнопки в `CellCard`.
- **C8.** Проверка баланса: скрипт `scripts/simulate.ts` прогоняет 1000 партий бот-против-ботов и печатает среднюю длину партии и винрейт по стартовой позиции.

### Блок D — Бонусы и наказания (свои механики) (✅ выполнено)
Реализация: режимы и их константы лежат в `modes.ts`. Логика в `engine.ts`: `transfer` → `state.pot`, `collectPot`, `timeout`, `startRound`, `finishByNetWorth`, `standings`. Хелперы `gameMode`, `rentMultiplier`, `netWorth` лежат в `economy.ts`. Ежедневный бонус считается в `dailyBonus.ts`. Тесты в `bonuses.test.ts`.

Капитал считается так: наличные + цена клеток (у заложенных вычитается сумма залога) + постройки по цене строительства. При равном капитале выше тот, у кого больше наличных, затем тот, кто раньше ходит.
- Новые поля. В `GameState`: `mode`, `round` (с 1, растёт в `nextPlayer`, когда ход возвращается к первому живому игроку) и `pot`. В `Player`: `idleStrikes`. В `NewGameOptions`: `mode` и `startBonus`. Новый Action — `TIMEOUT`, новых фаз нет.

Кто попал на «Нейтральную зону», забирает всю копилку. Если игрок банкротится перед банком, остаток его наличных в копилку не попадает.
- **Таймаут.** `TIMEOUT` штрафует `actingPlayer`: списывает `idleFine` только из наличных, ниже 0 не уводит и до банкротства не доводит. Затем за игрока делается одно действие `decideBotAction`. Любое своё действие обнуляет `idleStrikes`. Когда счётчик доходит до `idleStrikesLimit`, игроку ставится `isBot = true`. Таймер ведёт `useGame` (отсчёт перезапускается при каждом изменении состояния), отображает его `TurnTimer`. Чтобы движок мог вызывать бота, `bot.ts` больше не импортирует `engine.ts`.

В «Блице» первый игрок выигрывает заметно чаще (33%), это стоит сбалансировать. Аукцион (E) должен учитывать, что при таймауте за игрока решает бот.

### Блок E — Торговля и аукцион (✅ выполнено)
Реализация: мутации в `engine.ts` (`startAuction`, `advanceAuction`, `handOver`), чистые проверки в `economy.ts` (`minBid`, `canBid`, `tradableCells`, `tradeAssetsValid`, `canProposeTrade`, `tradeKey`, `EMPTY_OFFER`), решения бота в `bot.ts` (`decideInAuction`, `decideOnTrade`, `decideTradeProposal`, `tradeGain`), тесты в `trade.test.ts`. Новая фаза `'auction'`, поле `state.auction: { index, bid, leaderId, queue }`. Участвуют все живые: первым решает следующий по ходу, отказавшийся — последним. `BID { amount }` (целое, ≥ `bid + AUCTION_STEP`, ≤ наличных) переносит участника в конец очереди, `PASS` выводит его из торгов насовсем. Кому не хватает наличных на минимальную ставку, выбывает автоматически. Остался один лидер — он платит ставку банку (не в копилку). Не осталось никого — клетка остаётся у банка. Затем ход продолжается через `finishMove` (после дубля — снова бросок). Решает `queue[0]` (`actingPlayer`), таймаут работает и в торгах.
- **Обмен.** `PROPOSE_TRADE { trade: { from, to, give, take } }` (`TradeOffer = { cells, money, releaseCards }`) можно отправить только в свой ход в фазах `roll` / `isolation` / `end`. Одному адресату — не чаще раза за круг: `state.tradeRounds["<from>><to>"] = round`. Появляется фаза `'trade'` и поле `state.trade` (`PendingTrade`, в `resume` — фаза, куда вернуться). Решает адресат (`actingPlayer`) через `ACCEPT_TRADE` / `REJECT_TRADE`. Перед принятием активы проверяются заново. Нельзя передавать клетки кварталов с постройками. Заложенные клетки переходят вместе с залогом, без процента. Карточки освобождения переходят как есть.
- **Бот.** На торгах открывает с половины цены, повышает на 10% цены, предел — `price × k`: 1, 1.5 — если клетка из своего квартала или своей сети, 1.25 — если она закрывает квартал сопернику. Запас наличных 200₵. На предложение соглашается, если его выигрыш по `tradeGain` больше нуля и не меньше выигрыша партнёра. Оценка: цена клеток (у заложенных — минус залог) + сумма цен квартала за каждую монополию + 50₵ за карточку. В фазе `end` после застройки бот сам предлагает сделку, если ему не хватает одной клетки квартала. Сначала пробует обмен монополиями, иначе платит деньги. Доплату подбирает так, чтобы партнёр по этой же оценке выигрывал не меньше. Тому же игроку бот повторяет предложение не чаще раза в 5 кругов.
- **UI.** `AuctionModal` — торги: ставка, лидер, очередь, кнопки «мин. / +50 / +100 / Пас» и таймер. `TradeDialog` — составить предложение (кнопка «⇄ Обмен» в центре доски). `TradeProposal` — входящее предложение («Принять» / «Отклонить»). Кнопка «Отказаться» переименована в «На торги».

- Задел. Обмена в фазе долга нет: должник может только продавать и закладывать. Встречного предложения (контроффера) нет. Бот не предлагает обмен ради станций монорельса и инфраструктуры. При таймауте в фазе `'trade'` человеку-адресату начисляется штраф, и за него отвечает бот. В онлайне (G) сервер должен проверять, что `BID` / `PASS` пришли от `auction.queue[0]`, `ACCEPT_TRADE` / `REJECT_TRADE` — от `trade.to`, а `PROPOSE_TRADE` — от `trade.from`.

- **Деплой (делает пользователь).** В панели MonsterASP задать переменные окружения: `DATABASE_URL` (например, бесплатный Neon или Supabase, строка с `sslmode=require`), `BOT_TOKEN` (токен из @BotFather, не коммитить), `BOT_USERNAME` (без @) и `APP_SHORT_NAME` (short name из `/newapp` в @BotFather). После деплоя проверить в `/api/health`, что `storage: "postgres"` и `telegramAuth: true`. Локально: `npm run dev:server` (API на :3000) и `npm run dev` (Vite проксирует `/api`).
- Решения, которые я принял сам. Живые игроки ходят первыми в порядке входа, боты после них. Одинаковые имена различаются номером («Игрок 2»). Покинуть комнату можно только в лобби; из идущей партии игрок просто уходит в меню, за него доиграет таймер, а вернуться можно по коду. Ежедневный бонус в онлайне к стартовым деньгам не прибавляется. Сервер рассчитан на один процесс Node: кэш и очередь изменений хранятся в памяти.
- Задел. Ежедневный бонус пока хранится в localStorage, его нужно перенести на сервер по userId (таблица рядом с `rooms`) и учитывать в онлайне. Нет чата, нет выхода или сдачи из идущей партии, нет зрителей и нет ограничения на число комнат от одного пользователя. При нескольких процессах iisnode (`nodeProcessCountPerApplication > 1`) понадобится общая очередь, например блокировки в Postgres, а long-polling заменится на `LISTEN/NOTIFY`. Транспорт спрятан за `online/api.ts` и `useRoom`: если WebSocket на хостинге заработает, его можно подставить туда. Для H1 уже есть проверенный Telegram id (`tg:<id>`) и БД.
- **G1.** Проверить поддержку WebSocket на MonsterASP (iisnode + WebSocket в web.config). Если нет — long-polling / SSE.
- **G2.** Комнаты на сервере: `POST /api/rooms`, join по коду. Сервер хранит `GameState` и применяет `applyAction` из `src/shared`.
- **G3.** Клиент: режим «онлайн», синхронизация состояния.
- **G4.** Авторизация через Telegram `initData` (проверка HMAC на сервере с токеном бота из env). Токен не коммитить.
- **G5.** Приглашение друга ссылкой `t.me/<bot>/<app>?startapp=<roomId>`.
- **G6.** Хранилище (JSON-файл / SQLite / внешняя БД) — отдельное решение перед шагом.

### Блок H — Монетизация (после мультиплеера)
- **H1.** Косметика (скины фишек / доски) за Telegram Stars (`openInvoice`, серверная выдача).
- **H2.** Реклама / рефералка — отдельное решение.

Порядок блоков ниже: **I → J → K**. Темам (J) нужны переводимые тексты (I), а графике (K) — ассеты от темы (J). Блок H можно делать параллельно. Косметика H1 хорошо ложится на темы и скины из J и K.

### Блок I — Мультиязычность (i18n)
Цель: весь текст интерфейса, лога, карточек и ошибок сервера показывается на языке игрока. Первые языки — `ru` (по умолчанию) и `en`.
- **I1.** Библиотека — `i18next` + `react-i18next` (сверить API через Context7). Словари лежат в `src/client/i18n/<lang>.json`, ключи типизированы: TS должен ругаться на несуществующий ключ. Множественные формы делаются через `Intl.PluralRules` (встроен в i18next); «1 модуль / 2 модуля / 5 модулей» проверить тестом.
- **I2.** Выбор языка: сохранённый в `cyber-rent:lang`, иначе `Telegram.WebApp.initDataUnsafe.user.language_code`, иначе `navigator.language`, иначе `ru`. В меню есть переключатель. Язык ставится в `<html lang>`.
- **I3.** Вынести строки из `src/client` (`App.tsx`, `components/*`, `hooks/useRoom.ts`, `online/api.ts`) в словари. В компонентах не должно остаться русских литералов; проверка — `grep` по кириллице в `src/client/**/*.tsx`.
- **I4.** **Лог без готовых строк.** Сейчас `engine.ts` пишет в лог русский текст (`log(state, \`${player.name} покупает …\`)`). Нужно заменить `LogEntry.text` на `{ key, params }` (например `{ key: 'log.buy', params: { player: 'p1', cell: 12, price: 200 } }`). Параметры — это id и числа, не имена: имя игрока и название клетки клиент подставляет сам на своём языке. Движок остаётся чистым и ничего не знает о языке. Поднять `SAVE_VERSION`, обновить тесты, которые проверяют текст лога.
- **I5.** То же для карточек (`cards.ts`: `text` → ключ) и режимов (`modes.ts`). Сервер (`room.ts`, `api.ts`) отвечает кодом ошибки (`ROOM_FULL`, `NOT_YOUR_TURN` …), текст подбирает клиент.
- **I6.** Форматирование чисел и валюты через `Intl.NumberFormat` в одной функции `formatMoney` (символ валюты берётся из темы, см. J).
- **I7.** Проверить вёрстку на английском и на самом длинном варианте строк: кнопки на 320px не должны переноситься в три строки.

### Блок J — Темы (сменные сеттинги доски)
Цель: киберпанк — лишь одна из тем. Новые сеттинги (фермерство, спортивный менеджер и т. д.) добавляются одной папкой данных и ассетов, без правок движка.
- **Решение по умолчанию.** Тема — это «шкура» поверх общих правил: 40 клеток, цены, ренты, группы и эффекты карточек одинаковы для всех тем, так что баланс, боты и тесты общие. Тема меняет названия, тексты, цвета групп, символ валюты, фишки, звуки и графику. Если теме понадобится своя экономика, это отдельный шаг с тестами баланса (`npm run simulate`).
- **J1.** `src/shared/themes/types.ts`: `interface Theme { id; names: Record<Lang, ThemeTexts>; currency; groupColors: Record<DistrictGroup, string>; tokens; }`, где `ThemeTexts` — названия 40 клеток, групп, особых клеток (Старт, Изолятор, Нейтральная зона), колод и тексты 32 карточек по их `id`. Реестр `THEMES` и `DEFAULT_THEME = 'cyberpunk'` в `src/shared/themes/index.ts`.
- **J2.** Перенести киберпанк в `src/shared/themes/cyberpunk/`: названия из `board.ts`, тексты из `cards.ts`, ₵. В `board.ts` и `cards.ts` остаются только механика (тип клетки, цена, рента, группа, эффект). Движок перестаёт читать `BOARD[i].name`: имена нужны только клиенту (после I4 это уже так).
- **J3.** Тест `themes.test.ts`: у каждой темы на каждом языке есть все 40 названий, все карточки, все группы; нет пустых строк; нет запрещённых слов «Монополии» (список в тесте).
- **J4.** `GameState.themeId` задаётся в `createGame`, в онлайне — хозяином в лобби (`configureRoom`). Поднять `SAVE_VERSION`. Клиент получает тему через хук `useTheme(state.themeId)`.
- **J5.** Клиентские ассеты темы лежат в `src/client/themes/<id>/`: CSS-переменные цветов, иконки клеток, фишки, звуки; манифест подключается через `import()` лениво, чтобы в сборку сразу не попадали все темы.
- **J6.** Выбор темы в меню и в лобби: карточки тем с превью.
- **J7.** Вторая тема (например, «Ферма») как проверка: добавить её, не меняя ни строчки в `src/shared/game`. Если правка понадобилась — значит, граница проведена неверно, исправить интерфейс `Theme`.
- **Как добавить тему (записать в `docs/THEMES.md` после J7):** скопировать папку темы в `src/shared/themes/` и `src/client/themes/`, перевести тексты, нарисовать ассеты, зарегистрировать в `THEMES`, прогнать `npm test`.

### Блок K — Графика (Phaser или Babylon.js)
Цель: красивая доска с анимациями вместо DOM-клеток. React остаётся для меню, панелей, модалок и лога. Канвас рисует только доску, фишки, кубики и эффекты.
- **K1. Выбор движка — первым шагом, с прототипом.** Phaser (2D) — легче, быстрее грузится в Telegram WebView на слабых Android, подходит для «рисованной» плоской доски. Babylon.js (3D) — объёмная доска и камера, но бандл и нагрузка на GPU заметно больше. Рекомендация: Phaser, если нет цели сделать 3D. Прототип: доска + фишка + бросок кубиков. Замерить размер чанка (gzip), время до первого кадра и FPS на телефоне в Telegram. Решение и цифры записать сюда. Оба пакета — чистый JS, ограничение MonsterASP на нативные `.exe` при сборке их не затрагивает. Версию брать последнюю, API сверять через Context7.
- **K2.** Слой `src/client/render/`: интерфейс `BoardRenderer { mount(el), update(state, animFrame), setTheme(theme), resize(), destroy() }`, React-обёртка `<BoardCanvas>` вместо `Board.tsx`. Движок подключается через `import()`, чтобы меню открывалось без него. Клики по клеткам отдаются наружу колбэком (открыть `CellCard`), логика в канвас не попадает.
- **K3.** Анимации берутся из того, что уже есть: `state.moves`, `rollCount` и тайминги из `timing.ts` / `useAnimation`. Длительности не менять, иначе разъедутся с серверными дедлайнами (G).
- **K4.** Ассеты по теме (J5): атлас текстур на тему, бюджет — до ~1–2 МБ на тему. Картинки свои или CC0, источник и лицензию записывать в `src/client/themes/<id>/ASSETS.md`.
- **K5.** Эффекты: покупка (подсветка клетки цветом владельца), постройка модуля/небоскрёба, рента (перелёт монет), Изолятор, банкротство. При `prefers-reduced-motion` эффектов нет.
- **K6.** Фолбэк: без WebGL или при ошибке инициализации показывается старая DOM-доска (`Board.tsx` не удалять). Переключатель «Простая графика» в настройках.
- **K7.** Адаптивность и производительность: 320px, landscape, `devicePixelRatio`, пауза рендера, когда вкладка скрыта или Mini App свёрнут. Проверить в Telegram на iOS и Android.
